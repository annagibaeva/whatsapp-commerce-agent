# WCA v1 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Take v0 — proven on twenty cases and one mock calendar — to a real salon: durable state, a live calendar, reschedule/cancel, a WhatsApp Flow booking screen, and approved templates for one market. Then answer the four questions v0 left open, of which the commercial one matters most: what a booking actually costs to serve. Every one of these has to slot into the existing `propose → gate.evaluate → commit` sequence without adding a second way to write to a calendar.

**Architecture:** No new architecture. v1 is v0's existing seams (`CalendarPort`, `TransportPort`, dependency-injected stores) filled in with real or durable implementations, plus two new `Action` types and one new inbound surface. `gate.py` does not change shape; it gains one new check and one new optional input.

**Tech Stack:** Same as v0 — Python 3.12, `uv`, Pydantic v2, pytest, FastAPI/uvicorn at the edge, Anthropic API for extraction only. New: stdlib `sqlite3` for durable state (no new dependency — see Phase 1).

**Spec:** `docs/superpowers/specs/2026-09-09-v1-gap-analysis.md` (the gap analysis this plan implements), `docs/PRD-whatsapp-commerce-agent.md` §6/§11, `docs/superpowers/specs/2026-08-21-wca-v0-design.md`.

## Global Constraints

Everything in v0's plan still applies. Repeated here because every v1 task inherits it:

- Python **3.12**. `StrEnum`, `X | None` unions.
- Every Pydantic model: `model_config = ConfigDict(extra="forbid")`.
- **Library code never calls `datetime.now()`.** Every function takes `now`. The one standing exception is `transport/webhook.py`'s route handlers, which already read the wall clock at the edge (`create_app`'s `now` parameter) — new routes follow that same precedent, not a new one.
- Randomness only from a seeded `random.Random(seed)`.
- All timestamps timezone-aware UTC.
- Money is integer minor units.
- Model ids are exact strings, no date suffix. Never send `temperature`/`top_p`/`top_k`.
- `HOLD_TTL_SECONDS = 600` (`calendar/mock.py`), `WINDOW_HOURS = 24` / `ESCALATION_MARGIN_HOURS = 2` (`escalation.py`) stay the single source of truth — a durable or live store reads these, never redefines them.
- Test command is always `uv run pytest`.
- **Write plainly.**
- No new dependency without a reason as explicit as v0's FastAPI/uvicorn justification. `sqlite3` is stdlib — no addition to `pyproject.toml`. A live-calendar vendor SDK, if one is used at all, stays behind the narrow `CalendarClient` protocol in Phase 2 — this codebase never imports it directly outside `calendar/live.py`.
- `MockCalendar` and `FakeTransport` are never deleted. They are what makes the test suite run with no network. v1 durable/live implementations are added alongside them, always behind the same port, never replacing the in-memory ones as what tests inject.

## Phase 1: Durable state

**What's true at the end that wasn't true at the start:** every store `build_serve_app` wires now survives a process restart. Kill `wca serve` mid-conversation, restart it pointed at the same db file, and the conversation's facts, the dedup set, every audit record, every open hold, and every open escalation are still there. `MockCalendar`/`AuditLog`/etc. still exist and still back the test suite.

### Task 1: `src/wca/db.py` — connection and schema

**Files:**
- Create: `src/wca/db.py`
- Test: `tests/test_db.py`

**Interfaces:**
- Consumes: nothing.
- Produces: `connect(path: str | Path) -> sqlite3.Connection`, `init_schema(conn: sqlite3.Connection) -> None`.

**Done condition:** a fresh db file gets six tables (`audit_records`, `conversations`, `dedup_messages`, `holds`, `bookings`, `escalations`); calling `init_schema` twice on the same connection does not raise and does not touch existing rows.

```python
"""One sqlite file, one schema, one place both are defined.

Every durable store in this codebase (audit, conversation, dedup, the
hold ledger, escalations) opens its own connection to the same file via
`connect()` and calls `init_schema()` once at startup. `CREATE TABLE IF
NOT EXISTS` everywhere -- this file never drops or alters a table, so
running it against a db that already has data in it is always safe.
"""

from __future__ import annotations

import sqlite3
from pathlib import Path

SCHEMA = """
CREATE TABLE IF NOT EXISTS audit_records (
    proposal_id TEXT PRIMARY KEY,
    record_json TEXT NOT NULL,
    decided_at TEXT NOT NULL
);
CREATE TABLE IF NOT EXISTS conversations (
    thread_id TEXT PRIMARY KEY,
    last_inbound_at TEXT NOT NULL,
    facts_json TEXT NOT NULL,
    hold_id TEXT
);
CREATE TABLE IF NOT EXISTS dedup_messages (
    message_id TEXT PRIMARY KEY
);
CREATE TABLE IF NOT EXISTS holds (
    hold_id TEXT PRIMARY KEY,
    slot_id TEXT NOT NULL,
    thread_id TEXT NOT NULL,
    created_at TEXT NOT NULL,
    expires_at TEXT NOT NULL,
    released INTEGER NOT NULL DEFAULT 0
);
CREATE TABLE IF NOT EXISTS bookings (
    booking_id TEXT PRIMARY KEY,
    slot_id TEXT NOT NULL,
    thread_id TEXT NOT NULL,
    service_id TEXT,
    booked_at TEXT NOT NULL,
    idempotency_key TEXT NOT NULL,
    reminder_sent_at TEXT,
    cancelled_at TEXT,
    UNIQUE (idempotency_key)
);
CREATE TABLE IF NOT EXISTS escalations (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    thread_id TEXT NOT NULL,
    reason TEXT NOT NULL,
    raised_at TEXT NOT NULL,
    window_closes_at TEXT NOT NULL,
    template_name TEXT NOT NULL
);
"""


def connect(path: str | Path) -> sqlite3.Connection:
    conn = sqlite3.connect(str(path))
    conn.execute("PRAGMA foreign_keys = ON")
    return conn


def init_schema(conn: sqlite3.Connection) -> None:
    conn.executescript(SCHEMA)
    conn.commit()
```

Test proves this is not vacuous by checking `sqlite_master` directly, not just "no exception raised":

```python
def test_init_schema_creates_every_table(tmp_path):
    conn = connect(tmp_path / "wca.db")
    init_schema(conn)
    names = {r[0] for r in conn.execute(
        "SELECT name FROM sqlite_master WHERE type='table'"
    )}
    assert {"audit_records", "conversations", "dedup_messages", "holds", "bookings", "escalations"} <= names

def test_init_schema_is_idempotent_and_keeps_data(tmp_path):
    conn = connect(tmp_path / "wca.db")
    init_schema(conn)
    conn.execute("INSERT INTO dedup_messages VALUES ('m1')")
    conn.commit()
    init_schema(conn)  # second call, same connection
    row = conn.execute("SELECT message_id FROM dedup_messages").fetchone()
    assert row == ("m1",)
```

### Task 2: `SqliteAuditLog` — depends on Task 1, parallel with Tasks 3-4

**Files:** Modify `src/wca/audit.py`. Test: `tests/test_audit.py` (extend).

**Interfaces:** `SqliteAuditLog(conn: sqlite3.Connection)` implements the same three methods `AuditLog` does: `append(record) -> bool`, `records() -> tuple[AuditRecord, ...]`, `__len__`. Same dedup contract: `append` returns `False` on a repeat `proposal_id`.

**Done condition — the property that matters:** dedup survives a restart, not just a process lifetime. `AuditLog._seen` is a `set()`; that is the exact bug PRD's platform-constraints table warns about ("commit takes an idempotency key" only helps if the dedup that guards it doesn't reset). Prove it by closing the connection, reopening a fresh `SqliteAuditLog` against the same file, and appending the same `proposal_id` again.

```python
def test_dedup_survives_reopening_the_connection(tmp_path):
    db_path = tmp_path / "wca.db"
    conn1 = connect(db_path)
    init_schema(conn1)
    log1 = SqliteAuditLog(conn1)
    record = _audit_record(proposal_id="prop_0001")
    assert log1.append(record) is True
    conn1.close()

    conn2 = connect(db_path)
    log2 = SqliteAuditLog(conn2)
    assert log2.append(record) is False          # not a fresh in-memory set
    assert len(log2.records()) == 1               # not double-written either
```

This is the test that would pass trivially if `SqliteAuditLog` kept its own `set()` dedup on top of the table — the reviewer's check is: does the *second* `SqliteAuditLog` instance, built from nothing but the connection, already know about `prop_0001`? If dedup is implemented as a Python-side set instead of the table's `PRIMARY KEY` / a `SELECT` before insert, this test fails.

`AuditRecord` round-trips through `record_json` via `model_dump_json()`/`model_validate_json()` — no manual field mapping to drift out of sync with `models.py`.

### Task 3: `SqliteConversationStore` — depends on Task 1, parallel with Tasks 2, 4

**Interfaces:** `SqliteConversationStore(conn)` implements `get_or_create(thread_id, now) -> ConversationState`, `get(thread_id) -> ConversationState | None` — same signatures as `ConversationStore`.

**Done condition:** facts and `last_inbound_at` survive a restart; `add_facts` on the returned `ConversationState` has to actually persist — a `ConversationState` is a plain Pydantic object today with no write-through, so `get_or_create(...).add_facts(...)` mutating the object in place does **not** durably save unless the store's own `get_or_create`/an explicit `save` writes it back.
```python
def test_facts_survive_reopening_the_connection(tmp_path):
    db_path = tmp_path / "wca.db"

    init_schema(conn1)
    store1 = SqliteConversationStore(conn1)
```

### Task 5: Durable hold ledger — depends on Task 1

**Files:** Create `src/wca/calendar/ledger.py`. Test: `tests/test_calendar_ledger.py`.

This is the piece Phase 2 (`LiveCalendar`) and Task 6 (`SqliteCalendar`) both build on. It owns only the lease — "who holds this slot and until when" — never a booking. That split matters for Phase 2: a live calendar's bookings live in the external calendar's own data, not here.

**Interfaces:**
```python
@dataclass
class Hold:  # same shape as calendar/mock.py's Hold
    hold_id: str
    slot_id: str
    thread_id: str
    created_at: datetime
    expires_at: datetime
    released: bool = False

class HoldLedger:
    def __init__(self, conn: sqlite3.Connection) -> None: ...
    def create(self, slot_id: str, thread_id: str, now: datetime) -> Hold: ...
    def live_for_slot(self, slot_id: str, now: datetime) -> Hold | None: ...
    def get(self, hold_id: str) -> Hold | None: ...
    def release(self, hold_id: str, now: datetime) -> None: ...
    def expire_due(self, now: datetime) -> list[Hold]: ...
```

`create` does the same check-then-write `MockCalendar.hold` does (`ALREADY_HELD` / raise `HoldRefused`), against a `SELECT ... WHERE released=0 AND expires_at>?` instead of an in-memory scan, wrapped in a transaction (`BEGIN IMMEDIATE`) so two concurrent webhook workers can't both see "no live hold" and both insert one — the same race `MockCalendar`'s `threading.Lock` exists to close, now across processes, which is why a lock alone won't do here.

**Done condition:** a hold created before a restart is still live (and still blocks a second hold on the same slot) after one; `expire_due` releases it once its TTL has passed, exactly like `calendar/mock.py`'s reaper contract.

```python
def test_a_hold_survives_a_restart_and_still_blocks_a_second_hold(tmp_path):
    db_path = tmp_path / "wca.db"
    conn1 = connect(db_path); init_schema(conn1)
    HoldLedger(conn1).create("s1", thread_id="t1", now=NOW)
    conn1.close()

    conn2 = connect(db_path)
    ledger2 = HoldLedger(conn2)
    assert ledger2.live_for_slot("s1", now=NOW) is not None
    with pytest.raises(HoldRefused) as err:
        ledger2.create("s1", thread_id="t2", now=NOW)
    assert err.value.reason is RefusalReason.ALREADY_HELD

def test_two_concurrent_creates_on_the_same_slot_only_one_wins(tmp_path):
    # Two threads racing HoldLedger.create on the same slot_id/now.
    # Proves the BEGIN IMMEDIATE transaction, not just the Python-level
    # check, is what prevents the double-hold -- a plain SELECT-then-
    # INSERT with no transaction would let both threads pass the SELECT.
    import threading
    conn = connect(tmp_path / "wca.db"); init_schema(conn)
    ledger = HoldLedger(conn)
    results = []
    def attempt(thread_id):
        try:
            results.append(("ok", ledger.create("s1", thread_id, now=NOW)))
        except HoldRefused as e:
            results.append(("refused", e.reason))
    threads = [threading.Thread(target=attempt, args=(f"t{i}",)) for i in range(8)]
    for t in threads: t.start()
    for t in threads: t.join()
    assert sum(1 for r in results if r[0] == "ok") == 1
```

```python
def test_a_committed_booking_survives_a_restart_and_stays_deduped(tmp_path):
```

### Task 7: `SqliteEscalationBook` — depends on Task 1, parallel with Tasks 2-6

```python
"""What a real calendar has to do, and nothing else.

Kept to three methods on purpose. This codebase should never need to
import a vendor SDK's client directly outside calendar/live.py -- if a
new capability is needed later, it gets added here, deliberately, not
inherited by accident from whatever the SDK happens to expose.
"""

from __future__ import annotations

from dataclasses import dataclass, field
from datetime import datetime
from typing import Protocol


@dataclass(frozen=True)
class ExternalEvent:
    external_id: str
    slot_id: str
    starts_at: datetime


class CalendarConflict(Exception):
    """The client refused a write -- something else already has this slot."""


class CalendarClient(Protocol):
    def list_events(self, since: datetime, until: datetime) -> tuple[ExternalEvent, ...]: ...
    def create_event(self, slot_id: str, starts_at: datetime) -> ExternalEvent: ...
    def delete_event(self, external_id: str) -> None: ...


@dataclass
class FakeCalendarClient:
    """An in-memory stand-in for a real calendar's own state.

    Exists so LiveCalendar can be built and tested with no network and
    no salon credentials -- and so a test can mutate this independently
    of anything LiveCalendar itself did, simulating a walk-in the owner
    booked directly. That's the whole point of this class: it is the
    only way to write a test that proves LiveCalendar.view() sees a
    change it did not cause.
    """
    _events: dict[str, ExternalEvent] = field(default_factory=dict)
    _by_slot: dict[str, str] = field(default_factory=dict)
    _counter: int = 0

    def list_events(self, since: datetime, until: datetime) -> tuple[ExternalEvent, ...]:
        return tuple(e for e in self._events.values() if since <= e.starts_at <= until)

    def create_event(self, slot_id: str, starts_at: datetime) -> ExternalEvent:
        if slot_id in self._by_slot:
            raise CalendarConflict(f"{slot_id} already has an external event")
        self._counter += 1
        event = ExternalEvent(external_id=f"ext_{self._counter}", slot_id=slot_id, starts_at=starts_at)
        self._events[event.external_id] = event
        self._by_slot[slot_id] = event.external_id
        return event

    def delete_event(self, external_id: str) -> None:
        event = self._events.pop(external_id, None)
        if event is not None:
            self._by_slot.pop(event.slot_id, None)

    # Test-only helper -- simulates the owner booking a walk-in directly
    # in the salon's real calendar, bypassing this codebase entirely.
    def simulate_external_booking(self, slot_id: str, starts_at: datetime) -> ExternalEvent:
        return self.create_event(slot_id, starts_at)
```

### Task 11: `LiveCalendar.availability()` / `.view()` — THE live-read property test — depends on Tasks 5, 10

**Files:** Create `src/wca/calendar/live.py`. Test: `tests/test_calendar_live.py`.

This is the task the gap analysis §7 names directly: *"`view()` must be a live read, and every new inbound surface... must terminate in the same `propose → gate.evaluate → commit-or-release` sequence."* Half of that sentence is this task. `view()`'s `held_by_thread`/`hold_id` come from the `HoldLedger` (Task 5); `slot_exists`/`booked` come from calling `client.list_events(...)` fresh, every call — never a cached snapshot.

```python
"""A real calendar behind CalendarPort.

Two sources of truth, deliberately not merged into one cache: the hold
ledger is ours, the external calendar is the salon's. `view()`'s
`held_by_thread` comes from the ledger; `slot_exists`/`booked` come from
a live call to the client, every time this method runs. That live call
is not an optimisation to remove later -- it is the only way gate check
5 can catch a slot someone booked directly in the salon's calendar
between our hold and our commit. See test_calendar_live.py's
`test_view_reflects_a_change_the_ledger_never_saw` -- if this method is
ever rewritten to read from a periodically-refreshed cache instead, that
test starts failing, on purpose.
"""

from __future__ import annotations

from dataclasses import dataclass
from datetime import datetime, timedelta
from typing import Any

from wca.calendar.client import CalendarClient, CalendarConflict
from wca.calendar.ledger import HoldLedger
from wca.calendar.mock import HoldRefused, RefusalReason


@dataclass
class LiveCalendar:
    client: CalendarClient
    ledger: HoldLedger
    slot_starts_at: dict[str, datetime]   # the slots we know about and when they start

    def availability(self, now: datetime) -> tuple[str, ...]:
        booked_slots = {
            e.slot_id for e in self.client.list_events(now, now + timedelta(days=365))
        }
        return tuple(
            slot_id for slot_id, starts_at in self.slot_starts_at.items()
            if slot_id not in booked_slots
            and self.ledger.live_for_slot(slot_id, now) is None
        )

    def view(self, slot_id: str, now: datetime) -> dict[str, Any]:
        # Live, every call -- see the module docstring.
        starts_at = self.slot_starts_at.get(slot_id)
        window_start = (starts_at or now) - timedelta(days=1)
        window_end = (starts_at or now) + timedelta(days=1)
        external = {e.slot_id: e for e in self.client.list_events(window_start, window_end)}
        booked = slot_id in external
        hold = self.ledger.live_for_slot(slot_id, now)
        return {
            "slot_exists": slot_id in self.slot_starts_at,
            "booked": booked,
            "held_by_thread": hold.thread_id if hold else None,
            "hold_id": hold.hold_id if hold else None,
            "starts_at": starts_at,
            "hours_until": (
                (starts_at - now).total_seconds() / 3600 if starts_at is not None else None
            ),
        }
```

```python
class RefusalReason(StrEnum):
    NO_SUCH_SLOT = "no_such_slot"
    ALREADY_HELD = "already_held"
    ALREADY_BOOKED = "already_booked"
    NO_SUCH_HOLD = "no_such_hold"
    HOLD_EXPIRED = "hold_expired"
    NO_SUCH_BOOKING = "no_such_booking"     # NEW
    EXTERNAL_CONFLICT = "external_conflict"  # from Phase 2 Task 13, if that landed first

def cancel(self, booking_id: str, now: datetime) -> None:
    with self._lock:
        booking = self._bookings.get(booking_id)
        if booking is None:
            raise HoldRefused(RefusalReason.NO_SUCH_BOOKING, booking_id)
        del self._bookings[booking_id]
        # The idempotency key that produced this booking must not block
        # a fresh booking of the same slot later -- drop it too.
        stale_keys = [k for k, v in self._by_key.items() if v == booking_id]
        for k in stale_keys:
            del self._by_key[k]

def booking_view(self, booking_id: str, now: datetime) -> dict[str, Any]:
    """Read-only, gate-shaped -- same posture as view()."""
    booking = self._bookings.get(booking_id)
    return {
        "booking_exists": booking is not None,
        "thread_id": booking.thread_id if booking else None,
        "slot_id": booking.slot_id if booking else None,
    }
```

### Task 21: The commit-callers test — depends on Task 20 (needs cancel/reschedule to exist so the test covers the real, final surface)

**Files:** Create `tests/test_commit_callers.py`.

This is the second structural test the gap analysis requires by name: *"a test asserting the set of callers of `commit`, so a new one cannot be added silently."* Same AST-walking technique `test_gate_purity.py` already uses, so a reviewer already trusts the method.

```python
"""The invariant: `CalendarPort.commit` has exactly two callers in
src/, and every other write to the calendar goes through one of them.

Two, not one -- tools.py::request_booking is the gated production path;
harness.py::run_cases is the offline scorer, and it evaluates the gate
itself (see harness.py) before calling commit, so it is not a bypass.
A new caller -- a Flow webhook handler that "already validated" its
input and writes directly, a reschedule shortcut, anything -- has to
either route through request_booking or get added to EXPECTED_CALLERS
by a reviewer who has to look at this test and decide that's actually
correct. That friction is the point.
"""

import ast
import pathlib

SRC = pathlib.Path("src/wca")

EXPECTED_CALLERS = {
    ("wca/tools.py", "request_booking"),
    ("wca/harness.py", "run_cases"),
}


def _commit_call_sites() -> set[tuple[str, str]]:
    """(relative file path, enclosing function name) for every `.commit(`
    call anywhere under src/wca, found by walking the AST rather than
    grepping text -- so a call split across lines or reformatted still
    counts, and a comment or string containing the word "commit" never
    does."""
    sites: set[tuple[str, str]] = set()
    for path in SRC.rglob("*.py"):
        tree = ast.parse(path.read_text(encoding="utf-8"))
        for func in ast.walk(tree):
            if not isinstance(func, (ast.FunctionDef, ast.AsyncFunctionDef)):
                continue
            for node in ast.walk(func):
                if (
                    isinstance(node, ast.Call)
                    and isinstance(node.func, ast.Attribute)
                    and node.func.attr == "commit"
                ):
                    rel = path.relative_to(SRC.parent).as_posix()
                    sites.add((rel, func.name))
    return sites


def test_commit_has_exactly_the_two_known_callers():
    found = _commit_call_sites()
    assert found == EXPECTED_CALLERS, (
        f"commit() callers changed: {found - EXPECTED_CALLERS} added, "
        f"{EXPECTED_CALLERS - found} removed. If a new caller is "
        "correct, it must route through wca.tools.request_booking "
        "instead -- see this test's module docstring -- or this set "
        "needs a reviewed change, not a silent one."
    )
```

It should fail with exactly `{('wca/some_new_file.py', 'some_new_function')}` in the diff, not a vague assertion error.

### Task 24: `parse_flow_submission` — depends on nothing, parallel with Task 23

**Files:** Modify `src/wca/transport/whatsapp.py`. Test: `tests/test_whatsapp_client.py` (extend).

A Flow completion arrives as an `nfm_reply` inbound shape — structurally different from the button/list replies `parse_inbound`/`_visible_text` already handle, and it is not conversational text, so it gets its own function rather than being forced through `_visible_text`.

```python
def parse_flow_submission(payload: dict[str, Any]) -> FlowSubmission | None:
    """Pull a Flow's completed submission out of a webhook body.

    Structurally separate from parse_inbound: an nfm_reply is a
    service_id/slot_id pair, not something a customer typed, and
    treating it as text (the way a button tap's title is) would force
    the extractor to parse structured data back out of a string it
    never should have been. None for anything that isn't this exact
    shape, same posture as _visible_text -- an unrecognised payload is
    skipped, not raised.
    """
    for entry in payload.get("entry", []):
        for change in entry.get("changes", []):
            for message in change.get("value", {}).get("messages", []):
                if message.get("type") != "interactive":
                    continue
                interactive = message.get("interactive", {})
                if interactive.get("type") != "nfm_reply":
                    continue
                nfm = interactive.get("nfm_reply", {})
                try:
                    response = json.loads(nfm.get("response_json", "{}"))
                except json.JSONDecodeError:
                    return None
                return FlowSubmission(
                    message_id=message["id"],
                    thread_id=message["from"],
                    flow_token=response.get("flow_token", ""),
                    response_json=response,
                )
    return None
```

### Task 30: Sync mechanism for `approved`/`quality_rating` — depends on Task 29

**Files:** Modify `src/wca/cli.py` (new `wca templates sync` subcommand). Test: `tests/test_cli.py` (extend).

```python
def cmd_templates_sync(args: argparse.Namespace) -> int:
    """Apply a hand-maintained overrides file on top of salon.templates.json.

    Not an API call -- Meta does not expose deliverability reliably
    (PRD §11). `overrides` is a small {reason: {approved, ...}} JSON a
    human edits after checking Meta's console by hand. This command's
    job is just: apply it, and say what changed.
    """
    registry = load_templates(args.templates)
    overrides = json.loads(Path(args.overrides).read_text(encoding="utf-8"))
    changed = []
    updated = []
    for t in registry.templates:
        if t.reason in overrides and overrides[t.reason].get("approved") != t.approved:
            changed.append(t.reason)
            t = t.model_copy(update={"approved": overrides[t.reason]["approved"]})
        updated.append(t)
```

## Phase 7: Plan-and-act under a trajectory gate

**What's true at the end that wasn't true at the start:** the model chooses tool sequence, attempt count and when to give up; the gate remembers every attempt in a thread, not just the one in front of it; and a decomposition attack that a per-action gate cannot see by construction — book-then-amend, service substitution, fact-flip-after-block — has a named invariant and a failing test before this phase existed.

**The trade this phase makes, stated plainly.** `whatsapp-v1-plan-and-act-spec.md` §4 proposes the planner assemble the facts it cites, checked by a provenance ledger (I-1). This plan does not build that. Two things in this codebase already prove why: `propose()` (`src/wca/propose.py:31`) builds `cited_rules` itself from `matching_rules(ruleset, facts)` — the model never chooses which rules are cited, has never been able to since v0. And `tools.py::request_booking` (`src/wca/tools.py:230-246`) pops any model- or conversation-supplied `hours_until_appointment` and `requested_weekday` and recomputes both from the slot's own `starts_at`, with a comment naming the exact bug this closed: a model-supplied lead time let a first-colour booking through, a model-supplied weekday booked a Sunday. `DERIVED_FACTS`/`CONVERSATIONAL_FACTS` (`src/wca/tools.py:190-201`) already classify every fact the ruleset reads into "computed by this code" or "said by the customer" — there is no third channel today, and this phase does not open one.

So: **facts stay code-derived.** `DERIVED_FACTS` comes from the catalogue and the slot; `CONVERSATIONAL_FACTS` comes from the extractor over the customer's own words. A fact from anywhere else — the planner asserting a value with no computation and no customer message behind it — cannot enter `proposal.facts` at all. This is structural, not traced: there is nothing to audit because there is no path for it to happen, the same way `gate.py` cannot suggest a booking because `Verdict` has no field for one (`src/wca/models.py:1-7`). It is a stronger guarantee than a checked ledger and it costs nothing to enforce, because it is already enforced, by code written before this spec existed.

What the planner actually gets to choose is **which tools run, in what order, how many times, and when to stop.** That is real agency — it is what the spec is reaching for when it says "the model's job" changes from proposing one action to choosing a goal decomposition. The spec's I-2 (fact stability), I-3 (no blocked end-state by decomposition) and I-4 (budget) survive this trade unchanged, because none of them depend on the planner supplying facts — they constrain the planner's actions, which is exactly the space it now has freedom in. I-3 does the most work of the three: checks 1–4 already re-run in full on every fresh proposal, so a same-slot, same-service retry with unchanged facts is already caught without any of this phase's code. What checks 1–4 cannot see is a blocked booking reached by a *different path* — cancel-then-rebook, a decoy service first — where each individual step's proposal is well-formed and would pass on its own. That is the gap a per-action gate cannot close by definition, because "per-action" means it only ever sees the action in front of it.

One casualty, named up front: `expect_never`/`forbidden_end_states` cases that depend on the planner supplying a fake `hours_until_appointment` or `is_first_colour_visit` value to unlock its own booking (the spec's I-1 worked example) don't need testing here — that channel doesn't exist. The adversarial cases this phase adds (Task 48) target the channel that does exist: tool sequencing.

**Build this before Phase 1, not after.** Only Task 39 (the durable trajectory store) needs
Phase 1's `db.py`. Tasks 37, 38, 40, 41, 42 and 43 need nothing from it: a trajectory has to
outlive a conversation, not a process. So the shortest path to the thing this phase exists to
prove is **37 → 38 → 40 → 42**, entirely in memory, with `SqliteTrajectoryStore` deferred until a
real salon depends on it. Durability is correct and it demonstrates nothing; I-3 catching a
decomposition attack is the only part of this roadmap nobody else has built.

**Probe the adversarial scenarios against v0 first, before any of this exists.** Task 48 writes
them as trajectory cases, which needs Task 46's schema. That is the wrong order to *discover*
them in. Spend an hour first driving cancel-then-rebook, decoy-service-then-amend and
fact-flip-after-block through the current agent by hand and record what happens. Some will
already fail safely — the intro above predicts a same-slot retry does — and knowing which is how
you size this phase honestly. Write them after the planner exists and you are writing cases
against behaviour you have already watched, which is how a suite ends up unable to fail.

### Task 42: I-3 — no blocked end-state by decomposition — depends on Task 40, sequenced before Task 41's placement or after (order between the two doesn't matter — they check different things)

**Files:** Modify `src/wca/gate.py`. Test: `tests/test_gate.py` (extend).

This is the task the phase intro calls load-bearing. Checks 1–4 already catch a same-facts retry — `propose()` recomputes `cited_rules` fresh every call, `evaluate()` re-runs every veto fresh every call, so nothing about repetition alone slips through. What it cannot catch is the *same blocked outcome reached by a different sequence of well-formed steps* — book an unrestricted service at the slot, cancel it, rebook the restricted one at the same slot: `reschedule_booking` (Phase 3 Task 20) already routes the second half back through `request_booking`'s full gate check, so even this is mostly closed by construction — but only for the one path this codebase happens to have built. A trajectory gate should not depend on every future path happening to reuse `request_booking`; it should refuse the *outcome* directly, independent of path.

"Outcome" here is kept deliberately narrow and mechanical: the `(slot_id, service_category)` pair a `book`/`reschedule` proposal targets. If that exact pair was blocked earlier in this trajectory by any real block (not `OVERRIDE_MISSED`'s "might apply" noise — a genuine grounding or conclusion refusal), it stays blocked for the rest of the trajectory, full stop, regardless of which tool or how many steps produced this new attempt at it.

```python

    # intro in the plan for why checks 1-4 alone don't already cover
```

### Task 44: The bounded plan-act-observe-replan loop — depends on Tasks 37-43

**Files:** Create `src/wca/planner.py`. Test: `tests/test_planner.py`.

This sits above `agent.Agent`, not inside it. `Agent.run_turn`'s own `MAX_ITERATIONS = 8` loop (`src/wca/agent.py:46`) is unchanged and still bounds how many model round-trips happen within one HTTP turn. What's new is that a *trajectory* spans many turns of a thread — it is loaded, extended, and saved once per inbound message, the same granularity `ConversationState` already uses.

The plan is made explicit the same way every other model output in this codebase is made explicit: as a tool call. `submit_plan` joins `TOOL_SPECS` — not a real action, `gate.evaluate` never sees it, `tools.dispatch` never routes to the calendar for it — its handler in `planner.py` validates the steps, assigns a `revision` (one more than the trajectory's last), and returns them as the current plan. Every other tool call in that revision must name a `step_id` from `submit_plan`'s own output (Task 45).

```python
"""Plan -> act -> observe -> replan, bounded.

One inbound message triggers one pass through here. The trajectory is
loaded from the durable store (or created), extended by whatever this
pass does, and saved once at the end -- the same shape cli.py already
uses for ConversationState.

A replan is the model calling submit_plan again mid-turn or on a later
turn; the budget (gate.MAX_REVISIONS, gate.MAX_TOOL_CALLS) is enforced
by gate.evaluate itself (I-4), not duplicated here -- this module reads
the same two constants only to decide when to stop calling the model
at all and force an escalate, which is the one decision the gate
itself cannot make (the gate can refuse a proposal; it cannot make the
planner stop proposing).
"""

from __future__ import annotations

from wca.gate import MAX_REVISIONS, MAX_TOOL_CALLS, evaluate
from wca.models import Plan, PlanStep, Trajectory


def run_trajectory(
    ctx: ToolContext,
    agent: Agent,
    trajectory: Trajectory,
    turn_messages: list[dict[str, Any]],
) -> tuple[str, Trajectory]:
    """Runs one turn's worth of plan-and-act, returns the reply and the
    updated trajectory. Caller (cli.py) persists the trajectory."""
    reply = agent.run_turn(turn_messages)   # unchanged Agent.run_turn, MAX_ITERATIONS still applies
    trajectory = _fold_turn_into_trajectory(trajectory, agent, ctx)

    last_revision = trajectory.plans[-1].revision if trajectory.plans else 0
    if last_revision > MAX_REVISIONS or trajectory.tool_calls >= MAX_TOOL_CALLS:
        if not any(p.action.type == "escalate" and v.allowed for p, v in zip(trajectory.proposals, trajectory.verdicts)):
            # Budget spent and nothing escalated on its own -- force it.
            # This is Task 43's I-4 check reached the honest way: propose
            # escalate, let the gate confirm it's deliverable, record it.
            reply, trajectory = _force_escalation(ctx, trajectory)

    return reply, trajectory
```

```python
def _dispatch_checked(ctx: ToolContext, trajectory: Trajectory, name: str, args: dict[str, Any]) -> Any:
    step_id = args.get("step_id")
    current_plan = trajectory.plans[-1] if trajectory.plans else None
    pending_ids = {s.step_id for s in current_plan.steps if s.status == "pending"} if current_plan else set()
    if step_id not in pending_ids:
        # Refused before dispatch -- no gate call, no calendar call, no
        # audit-invisible side effect. The model sees this in its next
        # tool_result and has to either call submit_plan again (a real,
        # visible revision) or name a step_id that actually exists.
        return {"ok": False, "reason": f"no pending step_id {step_id!r} in the current plan revision"}
    return dispatch({k: v for k, v in args.items() if k != "step_id"} and ctx, name, args)
```

### The risk this phase exists to name

A loop whose purpose is turning blocks into bookings sits directly on top of a gate whose purpose is blocking. That is the whole risk surface of this phase in one sentence, and every task above is either building that loop (Task 44) or building something to keep it honest (Tasks 41-43, 45, 47-48). If any of those checks regress, the loop's own incentive — a replan is *supposed* to try again — points straight at exploiting the regression, not around it by accident.

The invariant that catches this, named exactly: **`override_01` must never reach a committed booking at any revision depth.** Not "at revision 0" or "on the first attempt" — at any depth this phase's loop can reach within its budget. Task 48's `override_01` case is written to prove exactly this, and Task 47's control arm is what proves the proof isn't vacuous: the same case must fail (evade) with the trajectory gate off, or the case set has stopped testing anything.
